Game selection now supports Classic, Quick and Team Up. Classic keeps the existing rules. In Quick, each seat begins with one token outside its yard and the first exact home token wins. Team Up requires four seats: seats 0/2 and 1/3 are partners, cannot capture each other, and must finish all eight tokens to win. A partner with all four tokens home skips their remaining turns. The ten-minute cutoff uses combined team home counts. Winning partners share the net prize equally; equal team scores split it across all four seats. Leaving or the sixth missed roll forfeits the whole team, so a team cannot remove unfinished tokens by sacrificing a player. This is disclosed before joining and in the leave confirmation.

Friends rooms use `mode: "private"` and a server-generated eight-digit room code. `GET /api/ludo/rooms/:code` returns the actual capacity, variant, entry, prize, occupancy and expiry before joining; it does not debit a wallet or disclose the seed. `POST /api/ludo/join` accepts `variant: "classic" | "quick" | "team"` and optional `roomCode`. The supplied terms must still match the room at join time. Private rooms are isolated from public queues and other account channels/agents, start only when full, and never fill with computers. Hosts may cancel with a refund for every participant; guests can cancel their own seat. An unfilled room expires after five minutes and refunds every entry exactly once. Private Team Up seats fill in the order 0, 2, 1, 3, pairing the host with the first friend. A refunded guest sees their own cancelled view even while the other seats continue waiting.

Variants and room codes are stored in the existing match JSON; the queue key separates variants and private rooms, so no database migration is required. Existing rooms without a variant continue as Classic. Join retries bind to mode, variant, capacity, entry and (when supplied) code. Browser coverage lives in `tests/ludo-modes.spec.ts`, included in the existing Ludo Playwright configuration; service coverage includes room expiry/cancellation, channel isolation, mismatched terms, Team Up settlement and Quick victory.

`/ludo` is an authenticated, server-controlled multiplayer game. Two seats use red/yellow; four seats use all colours. Players are matched by seat count, entry and account channel (B2B rooms also share the same agent). A full room starts immediately. After 20 seconds, remaining seats become visibly labelled Computer players.

Entries are ₹10, ₹50, ₹100 or ₹500. Joining reserves the entry in the existing shared wallet and creates a normal bet/report record. The first player to take four tokens home receives 90% of `entry × seats`; 10% is the platform commission. Computer seats are house-funded. A Computer win does not credit any human account. Waiting-room cancellation refunds the entry; leaving a started game forfeits it.

Every match has a fixed ten-minute limit from `startedAt`. At the cutoff, only the number of finished tokens determines winners; distance travelled is never a tiebreaker. All non-forfeited seats tied for the highest home count share the net prize, including a zero-home tie. Computer shares remain with the house. Paise are split evenly, with any remainder assigned in seat order. The turn scheduler and action endpoint both enforce the same cutoff under the match lock, and settlement credits each bet only once. The client displays the match countdown and each account's actual payout.

Rules: a six enters a token, exact roll to finish, safe star squares, captures return opponents to the yard, no stack blockades. Sixes, captures and reaching home grant another roll. Three consecutive sixes end the turn. Red starts. Each human roll/move allows ten seconds. Five consecutive server-driven dice rolls are allowed; missing the sixth roll forfeits the entry and removes that seat. A manual dice roll resets this counter. Token selection, single-token auto movement, chat, and page refresh do not reset it; Computer players are exempt. Bots make one action per second and use only the public board. A long server interruption may restart the action timer but never extends the match cutoff.

Match chat uses member-authorized GET/POST `/api/ludo/:id/chat`, private `ludo-chat:<userId>` notifications and polling recovery. Text is free; each of the 24 emoji sends costs ₹5, shown before tapping. Emoji characters in free text are rejected in favour of the priced tray. Messages render as plain text, have length/rate limits, and outsiders cannot read or subscribe. Leaving/finishing closes sending while retaining readable history. Chat does not change gameplay versions or deadlines. An emoji's debit (`adjustment`, `refType=ludo_emoji`) and message commit in the same transaction. A per-user request UUID deduplicates retries, including after match completion; uncertain sends are retained in session storage and expose a retry button. Migration `0058_ludo_chat` adds the message table; the schema is also generated into the isolated demo runtime.

Match state, deadlines, seat ownership and every accepted action are persisted in PostgreSQL. A row lock serializes actions and payouts. Join/action UUIDs support safe retries; expected versions reject stale clicks. Partial unique indexes prevent multiple active seats per account. Wallet ledger changes and bet settlement share the room transaction. `ludo:<userId>` WebSocket events contain a committed, member-specific public snapshot and an acknowledgement UUID visible only to the issuing account. Private snapshots update the board immediately; polling remains the reconnect fallback. The client rejects lower match versions even if an old response has a newer timestamp, and retains a bounded sequence of snapshots so React batching cannot skip a six before a yard exit. Dice and token animations run in order, including back-to-back turns, and the board is memoized independently of the clock. The server processes due rooms with four bounded workers and avoids unnecessary wallet-ledger reads/broadcasts during rolls and moves. Long server interruptions restart the action timer.

Each match commits to SHA-256 of a 32-byte random seed before play. Rolls use HMAC-SHA256 with message `ludo:v1:<matchId>:<zero-based nonce>:<block>`. Read bytes left-to-right, reject bytes ≥252, then take `byte % 6 + 1`. A new block is used only when needed. The seed and action/roll audit become available to participants at `/api/ludo/<id>/proof` once the match ends. The UI verifies the seed commitment and downloads that record. This is a reproducible server-seed commitment, not a third-party certification.

The additive `0057_ludo_matches` migration creates three tables and uniqueness/index constraints. Existing games and old application versions remain compatible. The normal API boot registers the game and starts the timer; no extra hosted service is required. Admins can pause new entries through the existing game control. In-progress games continue to settle.
